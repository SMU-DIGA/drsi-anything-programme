NS-RSI-Anything

Neuro-Symbolic Recursive Self-Improvement across General Domains

SMU-DIGA

Design Environments Results Progress Roadmap BibTeX GitHub

Deep RL updates weights. Prompt optimization tunes instructions. We let LLMs rewrite the program itself, keep a version only if it wins on seeds it never saw, and repeat.

TL;DR

An LLM writes a program that solves a task, such as an Atari bot, a robot-arm controller or a desktop agent. A population of LLM improvers (Codex CLI, Claude Code, DeepSeek) then improves that program over many generations, using only feedback from interaction with the environment. Promotion is gated on hidden seeds, and we evaluate on the game, embodied-robotics and computer-use benchmarks the community reports on most often.

Abstract

Deep reinforcement learning improves agents by adjusting weights. Recent evidence suggests that coding agents editing hand-written programs can reach competitive scores on Atari, MuJoCo and VizDoom without any gradient step, and that cross-domain recursive self-improvement loops benefit from frozen evaluation protocols. NS-RSI-Anything combines the two into a neuro-symbolic loop: neural models (LLMs) do the reasoning and the editing, while what is learned is stored symbolically, as readable, testable code and notes that persist across generations. A program, consisting of a policy, its skills and its notes, is improved generation after generation by a heterogeneous population of LLM improvers. Each candidate is re-evaluated in an isolated process and promoted only by a paired test on hidden seeds. We study when such loops keep improving, what transfers across tasks, and how they compare with RL under the same environment-step budget, on games, embodied manipulation (LIBERO, ManiSkill3, SimplerEnv, RoboTwin 2.0) and computer use (OSWorld).

Design

Improve the program, not the weights.

A program is the whole "heuristic system": the policy, its state detectors and skills, and notes holding environment facts, failed ideas and a dated changelog. Each generation runs four steps.

1

Propose

The incumbent is copied into one isolated workspace per improver, with a task brief, per-seed feedback, the full history of earlier attempts, and an evaluator restricted to the train seeds.

2

Re-evaluate

Candidates are re-scored independently. The environment runs in one process and the policy in another, so a policy never sees the reward, the seed or the environment object.

3

Promote

The best candidates face the incumbent on hidden dev seeds under a paired bootstrap gate. Test seeds are used once, at the end.

4

Simplify

The winner is simplified and kept only if its dev score does not drop. This counters the build-up of patches.

The gate caught overfitting

In generation 3 a candidate scored the maximum on all 8 train seeds but only 714 on dev: it had tuned itself to the few train trajectories. It was rejected. Generation 4 reached 864 on every dev seed and then on every one of the 64 test seeds, which no improver or gate had ever touched.

Montezuma's Revenge without exploration bonuses

The promoted program follows an explicit room-by-room route over RAM state (room, position, inventory, enemy positions, and a laser countdown it discovered). It times jumps on the skull's live position and laser crossings on the countdown, collects keys, treasures and a sword, and opens four doors. Where a respawn keeps the inventory, it loses a life on purpose as a shortcut back. Caveat: without sticky actions, different seeds mostly shift start-up timing, so dev mainly tests robustness to timing. Evaluations with sticky actions are next.

Ms. Pac-Man as graph search

The program decoded the maze layout, every dot and power pellet, and the ghosts' positions and frightened timers from RAM. It plans over a maze graph with tunnel links, weighting routes by distance to active ghosts and turning to chase when they are frightened. Train episodes ranged from 8,370 to 30,611 points.

Cost: Breakout used 23.9 M environment steps over 4 generations, counting every evaluation by every improver. Sample efficiency is not yet a strength of this loop.

How to read these numbers

No demonstrations and no learned weights: every policy is readable code. State mode is easier than the VLA setting and is not comparable to it. Vision mode is the closest match, but it uses depth and camera calibration, which the VLA models do not. Programs contain routines per task family and generalize across unseen initial scenes, which is what LIBERO's protocol tests.

What the programs found by probing

The vision program measured that its agent-view estimate of a bowl's centre is biased by about 4 cm, so it re-centres with the wrist camera before grasping. The LIBERO-10 program worked out each goal condition (e.g. the stove counts as on once its knob turns past about 0.45 rad) and found initial scenes where objects fly off the table on the first step, which no policy can solve.

LIBERO-Spatial vision has stayed at 95.0% on dev for three generations; candidates now enter the dev gate on ties, and programs may learn from their own train episodes. ManiSkill3 is queued.

Running: generation 1

OSWorld, LibreOffice Calc and OS tasks (71 tasks, split 23 / 24 / 24 into train, dev and test), scored by OSWorld's own checkers. The program decides every action in code, including running code inside the desktop and reading its output. Two settings are compared: pure code, and code that may also ask one fixed small model (Qwen3.5-2B) typed multiple-choice questions, in the style of TypeSafe's Jev. The model never writes text or actions; it returns a probability per option and acts as a smart if-statement inside the program. In both settings the program may learn a memory from its own train episodes, frozen during dev and test.
